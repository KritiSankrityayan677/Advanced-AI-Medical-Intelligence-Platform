# NeuroVision AI — Brain Tumor MRI Analysis Platform

An end-to-end AI system for automated brain MRI classification, explainability, and AI-assisted preliminary radiology reporting.

**Live Demo:**
- Frontend (Streamlit): https://neurovision-ai.streamlit.app/
- Backend API (Railway, Swagger docs): https://neurovision-ai.up.railway.app/docs

> ⚠️ This platform is a research and educational tool. All outputs are preliminary and require review by a qualified radiologist. It does not provide a medical diagnosis.

## What This Platform Does

1. **Classifies** a brain MRI scan into one of four categories: glioma, meningioma, pituitary tumor, or no tumor detected.
2. **Explains** the classification visually using Grad-CAM, highlighting the image region that most influenced the model's decision.
3. **Contextualizes** the result with a plain-language interpretation and general clinical/anatomical background for the predicted class.
4. **Reports** the finding in a structured, standard radiology format (Clinical Indication, Technique, Findings, Impression, Recommendations), generated by an LLM and reviewed against safety guardrails.
5. **Records** every analysis to a database so past scans can be reviewed later.
6. **Serves** all of the above through a REST API and a user-friendly web interface.

                     │ DenseNet-121    │      │ Grad-CAM        │     │ LLM Report      │
                     │ (Classification)│      │ (Explainability)│     │ Generator (Groq)│
                     └────────────────┘      └────────────────┘     └────────────────┘
                              │
                              ▼
                     ┌────────────────┐
                     │ SQLite Database │

The frontend is a **thin client** — it holds no business logic and only calls the REST API. This means the backend can be redeployed, scaled, or swapped independently of the UI, and could equally serve a mobile app or a different frontend framework without any backend changes.

## Model Performance (Phase 1)

Trained via transfer learning on DenseNet-121 (ImageNet-pretrained), fine-tuned on the Brain Tumor MRI Dataset (Kaggle, Masoud Nickparvar).

| Metric | Value |
|---|---|
| Test accuracy | 94.7% |
| Macro ROC-AUC | 0.989 |
| Glioma sensitivity | 0.813 |
| Meningioma sensitivity | 0.990 |
| Notumor sensitivity | 0.998 |
| Pituitary sensitivity | 0.988 |

**Note:** Glioma showed comparatively lower sensitivity than the other three classes. This is discussed in the accompanying project report along with the Grad-CAM analysis used to investigate it. In a screening context, this class-level gap is treated as a priority limitation rather than something to obscure behind aggregate accuracy.

## Explainability (Phase 2)

Grad-CAM is used to visualize the image regions that most influenced each classification. The resulting heatmap is overlaid on the original scan and returned alongside every prediction.

Sample visualizations are available in `docs/`:

| Class | Heatmap |
|---|---|
| Glioma | `docs/gradcam_glioma.png` |
| Meningioma | `docs/gradcam_meningioma.png` |
| Notumor | `docs/gradcam_notumor.png` |
| Pituitary | `docs/gradcam_pituitary.png` |

The platform also generates a short plain-language interpretation of the region of interest, combining the model's output with general anatomical context for the predicted class (e.g., typical tumor location). This never claims to identify a specific mass in the patient's scan — it explains, in neutral clinical language, what the highlighted region and classification are generally consistent with.

## LLM-Generated Reports (Phase 3)

Reports follow the standard five-section radiology format:

1. **Clinical Indication**
2. **Technique**
3. **Findings**
4. **Impression**
5. **Recommendations**

**Safety guardrails built into the prompt and enforced in code:**
- The system never states a diagnosis — only a preliminary, structured draft for professional review.
- Confidence is reflected honestly; results below 70% are explicitly flagged as low-confidence.
- The model is instructed not to invent patient history, measurements, or findings beyond what the classifier and Grad-CAM actually produced.
- Writing style avoids personifying the software (no "the AI thinks..."), matching real radiology reporting conventions.
- A disclaimer is always present in the final output — enforced in code as a safety net even if the LLM omits one.

**LLM provider:** Groq (free tier), configured via environment variables (`LLM_PROVIDER`, `LLM_MODEL`, `GROQ_API_KEY`). The generator is built behind an abstract `ReportGenerator` interface (strategy pattern), so the underlying provider can be swapped for another (e.g., OpenAI, Anthropic, a local Ollama model) by adding one new class — no other code changes required.

## REST API (Phase 4)

Interactive documentation (Swagger UI): **https://neurovision-ai.up.railway.app/docs**

| Endpoint | Method | Description |
|---|---|---|
| `/health` | GET | Liveness check; reports model architecture and device |
| `/predict` | POST | Upload an MRI, receive predicted class and probabilities |
| `/predict/report` | POST | Upload an MRI, receive prediction, Grad-CAM heatmap (base64 PNG), XAI interpretation, and full structured report |
| `/history` | GET | Paginated list of past predictions (`?limit=&offset=`) |
| `/history/{id}` | GET | A single historical prediction by ID |

Design notes: Pydantic schemas validate every request/response; invalid uploads return proper HTTP 400 errors; uploaded files are handled via temporary files that are always cleaned up; CORS is enabled for browser-based frontends; heatmap images are base64-encoded into the JSON response so the entire result travels in a single call.

---

## Database (Phase 5)

Every `/predict` and `/predict/report` call is persisted via SQLAlchemy to SQLite. Each record stores: timestamp, filename, predicted class, full probability distribution (JSON), confidence, the generated report text and model name (if applicable), and the model architecture that produced it — the last field allows future retrained models to be filtered and compared against historical predictions.

The database layer is cleanly separated: `models.py` defines the schema, `crud.py` provides reusable data-access functions, `database.py` manages the engine/session. Swapping SQLite for PostgreSQL in production requires changing only the connection string.

---

## Web Frontend (Phase 6)

Built with Streamlit, structured as three pages:

- **Analyze a Scan** — upload an MRI, run classification, review the region-of-interest overlay and plain-language interpretation, then optionally generate the full structured report on demand.
- **Past Scans** — browse prediction history in expandable cards.
- **About** — plain-language explanation of the tool's purpose, scope, and safety information.

The report generation step is intentionally separated from classification (a distinct "Generate report" action) so that the more expensive LLM call only runs when the user actually wants the full report, rather than on every upload.

## Deployment (Phase 7)

The system is deployed as two independently hosted services:

| Service | Platform | URL |
|---|---|---|
| Backend API | Railway (Docker) | https://neurovision-ai.up.railway.app |
| Frontend | Streamlit Community Cloud | https://neurovision-ai.streamlit.app |

The backend is containerized with a `Dockerfile` (Python 3.12-slim base image, system libraries for OpenCV/Pillow, single-worker Uvicorn) so it runs identically in any Docker-capable environment. The frontend reads the backend's URL from an environment variable/secret (`MEDICAL_AI_API_URL`), so the same frontend code works against a local API, Render, Railway, or any future host without modification.

### Running locally

**Prerequisites:** Python 3.12, Git.

```bash
git clone https://github.com/KritiSankrityayan677/Advanced-AI-Medical-Intelligence-Platform.git
cd Advanced-AI-Medical-Intelligence-Platform

python -m venv venv
# Windows:
.\venv\Scripts\activate
# macOS/Linux:
source venv/bin/activate

pip install -r requirements.txt
pip install -r frontend/requirements.txt
```

Create a `.env` file at the project root (see `.env.example`):

```
GROQ_API_KEY=your_groq_api_key_here
LLM_PROVIDER=groq
LLM_MODEL=openai/gpt-oss-20b
```

**Terminal 1 — start the API:**
```bash
uvicorn app.api.main:app --reload
```
Visit `http://127.0.0.1:8000/docs`.

**Terminal 2 — start the frontend:**
```bash
streamlit run frontend/app.py
```
Visit `http://localhost:8501`.

### Running with Docker (backend)

```bash
docker build -t neurovision-ai-backend .
docker run -p 7860:7860 --env-file .env neurovision-ai-backend
```

### Running the test suite

```bash
pytest -v
```

Tests are split so that logic and contract tests run without external dependencies (model weights, API keys), while integration tests skip gracefully when those aren't available — this is what allows the suite to run cleanly in CI. See `.github/workflows/tests.yml`.

## Key Design Decisions

- **Modular architecture.** Configuration, model loading, prediction, explainability, LLM reporting, database access, and the API are each isolated in their own module with a single responsibility. Every later phase (API, frontend) reuses the same functions rather than duplicating logic.
- **Config-driven, no hardcoded values.** Class names, input size, normalization stats, and the Grad-CAM target layer are all read from `model_metadata.json` at runtime. Retraining the model with different parameters flows through the whole system without code changes.
- **Clinical metrics over raw accuracy.** The model is evaluated with per-class sensitivity/specificity and macro ROC-AUC, because in a screening context a false negative is more costly than a false positive — and accuracy alone would obscure the model's actual weak point (glioma).
- **Anatomically valid augmentation.** Training augmentation deliberately avoids operations that would produce anatomically implausible brains (e.g., vertical flips, large rotations), reflecting the difference between natural-image augmentation and medical-image augmentation.
- **Swappable LLM backend.** The `ReportGenerator` abstract interface means the Groq implementation can be replaced by another provider by adding a single new class.
- **Two-layer safety net on disclaimers.** The LLM is instructed to always include a disclaimer, and the application code independently inserts one if it's ever missing — the safety-critical behavior does not rely on the LLM alone.
- **Restrained explainability claims.** Grad-CAM heatmaps and the accompanying interpretation describe *where the model looked* and *general clinical context for the predicted class* — they never claim to identify a specific mass or pathology in the patient, which would overstate what the method actually supports.
- **Automated testing and CI.** A 24+ test suite (config, predictor, Grad-CAM, report generator, API, database) runs on every push via GitHub Actions, catching regressions before they reach production.

## Known Limitations

- **Glioma sensitivity (81.3%)** is lower than the other three classes; the confusion matrix shows misclassification primarily toward meningioma and notumor. This is documented rather than hidden and is a candidate for future improvement (e.g., focal loss, additional glioma-focused data augmentation).
- **Free-tier hosting constraints.** Both the API and frontend run on free hosting tiers, which may introduce cold-start delays after periods of inactivity.
- **Not a diagnostic device.** This platform is a research and educational project. It has not been validated or approved for clinical use, and all outputs require review by a qualified radiologist before any clinical decision.
